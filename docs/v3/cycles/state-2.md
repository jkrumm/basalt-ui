# State cycle 2

One data page built on master's published surface, fresh after cycle 1's fixes: a support-ticket list with four URL filters (a date range, a multi-select, a search and a toggle) in the page bar, a table and a chart of the same query behind the page tabs, a pushed list query bound to a channel, a polled queue figure, a connection indicator, and a row that opens an edit form with a draft, validation, `toSubmitErrors` and `FormFooter`. Then the user actions of the brief, run in Chrome against the playground build. Protocol: `docs/v3/CYCLES.md`.

The cycle has not converged: 1 P1, 8 P2 and 4 P3. Cycle 1's fixes hold where the cycle met them: the multi survives a second Escape, a restored draft draws every field, the desktop filter row has its own `Reset all`, `spec` takes the range and multi handles, the tabs and the sheet bind a handle, the v3 `ChartCard` and `createChannel` come from their subpaths, and the build needs no cast. Its one waiver is the 2.x theme guard reading a v3 `Select` in a `FormField` as a bare filter (state-2.13). Share, reload, back and forward put the page back exactly. The P1 is new: closing the record from the mutation's `onSuccess`, the natural place, unmounts the form before `useFormDraft` sees the submit end, so the draft outlives the save and the next open says "Draft restored" over the saved ticket (state-2.4). Two of cycle 1's fixes landed on a surface a v3 app does not reach: the offline branch went into the 2.x `BasaltDataTable`, so the v3 `DataTable` still paints skeleton rows offline (state-2.5), and the router's `live` option cannot be written for the client the router builds itself (state-2.1). The app wrote no `useState` and no manual URL read, and about 12 lines of glue against cycle 1's 44.
