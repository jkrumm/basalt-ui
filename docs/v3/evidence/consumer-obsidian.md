# Consumer audit: basalt-ui-obsidian (`~/SourceRoot/basalt-ui-obsidian`)

Audited 2026-11-09, read-only. basalt-ui 2.28.0 (exact pin, `apps/demo/package.json`, library devDep + peer `^2.7.3`). Public repo, own code, citeable.
Method: perl import parse over 99 non-generated .ts/.tsx files (`/tmp/obs-imp.tsv`), grep, `git log`, `docs/waves/**`.

## 0. What the app is (fact)

- Read-only, offline-capable PWA reader for an Obsidian vault ("Brain", served as brain-web on the mini). No auth, no mutations, no forms, no charts, no tables, no cards, no notifications, no realtime, no SSR. Static `vault.json` + `search-index.json` built at deploy time (`apps/demo/vite-plugins/vault-data.ts`), precached by a service worker.
- Three workspaces: `obsidian-vault-core` (framework-free parser, zero basalt), `basalt-ui-obsidian` (React library, 0.0.0, unpublished, README "v0"), `apps/demo` (the reader). 6309 src lines + 3931 test lines. 28 test files, 260 tests (`docs/waves/PLAN.md` Appendix B).
- It is the one consumer that is a **derivative package atop basalt-ui**: a library of vault components (`NoteView`, `VaultNav`, 5 panels, `useObsidianMarkdown`) whose only basalt coupling is `basalt-ui/content` + `basalt-ui/tokens` (types and `VX`), plus Mantine directly.
- Consumer-sized signal: tiny surface, 62 commits since 2026-08-11, 28 of them basalt version bumps (`git log` grep) in 11 weeks (1.14.0 -> 2.28.0). Churn is dominated by upgrades, not features.

## 6. A derivative package atop basalt-ui: what it looks like, what v3 must expose

Shape today (fact): `basalt-ui-obsidian` is `peerDependencies` basalt-ui `^2.7.3` + `@mantine/core|hooks ^9.7.0` + react-markdown stack; `dependencies` only its sibling core; unbundled ESM + copied CSS modules + `.d.ts` (`package.json`, `tsup.config.ts`). Components take **render seams** (`renderLink`, `renderIcon`, `renderChevron`, `hrefFor`) via a `VaultProvider` context (`src/context.tsx`) so the library stays router-free and icon-free. It extends basalt through exactly: `Markdown` props (`remarkPlugins`, `components`, `fenceRenderers`, `sanitizeSchema`), `Callout`, `ArticleLayout`, `VX` tokens, `--vx-*` custom properties.

What worked as a package pattern:

- Extension by **props on a headless-enough core** (`MarkdownProps`), not by forking. Types exported so the package can `Pick<MarkdownProps, ...>` (`use-obsidian-markdown.ts:42-45`).
- Sanitize-schema merge as a first-class export (`mergeSanitizeSchema`), since the content renderer sanitizes last and unconditionally.
- Render seams in context keep it framework-neutral and testable.

What hurt:

- The package cannot use basalt's shell, stores, nav, controls without taking the full provider tree; it used `@mantine/core` leaf components directly and avoided basalt-ui/state, so it re-grew persistence (#10).
- The package is pinned to a Mantine major through basalt (peer `@mantine/core ^9.7.0`). A v3 shadcn move breaks all of its components, not only basalt imports.
- Peer-range semantics: floor `^2.7.3` chosen as "what we proved on", not "what the code needs" (`PLAN.md` D2). No way to declare "needs basalt contract X".
- CSS modules in a library need a copy step and a consumer bundler contract.
- It had to re-implement a11y of a third-party primitive because it could not own the `<li>`.

## 9. Carry-over lessons for the v3 design (summary)

1. Silent drift is the cost. Any value an app can override (token, header height, breakpoint) should be typed config with a changelog, or v3 should provide a check that flags overrides whose upstream default moved.
2. An app should never have to select framework DOM class names. Zero such selectors is a testable invariant.
3. Providing a typed content extension API was the best decision; make every area look like `Markdown` (props-in, seams, memo rules documented).
4. Provide primitives that libraries can use without taking the whole framework: store, tokens, content, tree. Keep the shell separable.
5. Shipped rules must each be enforced or labeled "advice". The state rule was ignored 4 times without a failing gate.
6. Skills/rules must be scoped by app type (reader, dashboard, tool). A reader loaded chart/controls rules for nothing.
7. Per-bump work should be one range-aware migration summary and a codemod/`doctor --fix`, not 28 hand-checked commits.
