Date 2026-11-09. **F** = observed fact (ran it, or read installed source / cited page). **J** = my judgement. Spike = scratch dir outside every repo (`/tmp/guardrails-agent/spike`, bun install, installed from npm under a 3-day min-release-age, so oxlint 1.92.0 not 1.93.0). ## 0. Verdict in eight lines

1. **F** The lint layer for a Tailwind+shadcn world is now mostly buyable. Two JS plugins run on oxlint and I ran both: **`@shadcn/lint` 0.2.5** (official, shadcn-ui org, created 2026-09-14) and **`oxlint-tailwindcss` 1.17.1** (one maintainer, created 2026-03-14). Together they cover arbitrary values, palette/hardcoded colours, unknown classes, class order, inline style, className tampering on owned components (`no-restyle`), and hand-rebuilt components (`no-borrowed-component-styles`). `self-guardrails.md` section 5 assumed T5/T6 were "own"; T6 is bought, T5 is half bought.
2. **F** shadcn's own evals (vendor, 150+ runs) say the delivery channel matters more than the rule text: with diagnostics every model hit zero findings in one round at 10-48% lower correction cost than rules-text-only; Haiku failed a task under rules-only (docs/evals.md). **J** This is the best external evidence for "skills teach, rules guarantee".
3. **F** Type-aware linting is stable (tsgolint 7.0.2006 on TypeScript 7.0.2, ran it) but **custom JS-plugin rules cannot be type-aware**. So: types for what types express, built-in tsgolint rules for generic hygiene, syntactic custom rules for the rest. No third path.
4. **F** TypeScript 7 (`tsc` native) is stable and 6.9x faster on this repo: PKG `tsc -p .` 11.3 s (6.0.3) vs 1.66 s (7.0.2), both clean. Tool APIs (typescript-eslint, Volar) stay on TS 6 until 7.1 (beta 2026-10-20, stable tentatively late Nov).
5. **F** Tailwind cannot be closed against arbitrary values. `--color-*: initial` removes palette utilities, `bg-[#316ff6]` still compiles (tailwindcss.com docs). The lint rule is the only gate, and removed classes fail silently without `no-unknown-classes`.
6. **F** Rules must be scoped by zone. On the console's vendored `components/ui/*` (9 files) the buyable rules fire 67 times (45 restricted-variant + 22 arbitrary: `dark:`, `has-[..]`, `data-[..]`, `origin-(--transform-origin)`), i.e. shadcn's own output violates a strict preset.
7. **F** Skills have thin evidence. No independent before/after study of any design skill on visual slop; one LLM-judged benchmark had Anthropic's frontend-design skill at -1.8 vs no-skill; a Baidu benchmark of 31 web skills found injected skills lowered Pass@2 by 1.3-4.2 pp, helped only 17-36% of pairs, and the reliable gain came from anti-pattern rules. Impeccable's own docs say most slop is caught by a hook, not the skill.
8. **J** v3 guardrail stack: closed `@theme` + types + `@shadcn/lint` + `oxlint-tailwindcss` (both pinned) + one small basalt plugin for what neither can express + tsgolint + a post-edit/Stop hook that returns diagnostics to the agent + geometry/shot gates. Delete the regex guard and most of the 4,382-line plugin.

## 4. Verified invariants and traps

- **F** `extends` replaces `no-restricted-imports` options wholesale. Ran on oxlint 1.92.0: base bans `@radix-ui/react-dialog` + `@visx/*`, extending config sets only `lodash`; result: only `lodash` reported. Matches `configs/oxlint-plugin.js:60-76` (I3 in `self-guardrails.md`). **J** Keep every boundary as a plugin rule with its own id; a consumer can then only switch it off by name.
- **F** oxlint option validation is strict: `no-restricted-classes` takes `patterns: [{pattern, message}]` and `classes: []`; a wrong key aborts the whole run ("Failed to setup JS plugin options"), so a shipped preset needs a smoke test per rule.
- **F** `oxlint-tailwindcss` tests each regex against the whole class string including variants (`^dark:`, `^(sm|md):` work); `no-arbitrary-value` has `allow`, `allowVariables`, `entryPoint`.
- **F** `@shadcn/lint` `allow: ["layout"]` includes width and height; `deny` closes them. Entries match base classes ignoring variants/important/negative/opacity; allowing `p-*` still lets `no-arbitrary-values` police `p-[13px]` (docs/rules.md).
- **F** `@shadcn/lint` resolves components via `components.json`, follows re-exports and renamed imports, and does not treat a same-named package component as a design-system component (docs/how-it-works.md). Better than basalt's import-provenance code (`oxlint-plugin.js:2008-2100`, ~1,100 lines serving 3 rules) for the same job.
- **F** Neither plugin lints `.css`, `@theme`, or Vue/Svelte/Astro templates (oxlint limit). Tailwind classes in template markup need ESLint; irrelevant for a React-only v3.
- **F** Tailwind `@source not inline(...)` blocks named utilities from generation; docs do not say whether it blocks arbitrary-value candidates. `@import "tailwindcss" important` is specificity, not restriction. `@theme static` only forces emission.
- **F** oxlint switches to a terse output format when it detects an agent runs it (oxlint-tailwindcss ai-agents page). **J** Free win for hook output size.

## 9. Recommendations for v3

Carry over:

1. Triad: surface registry -> tagged rule bullets -> generated coverage with honest `not guarded` lines; tag F2 (tag implies negative test).
2. Waiver grammar with unknown-id-waives-nothing and `--audit-allows` (I1, I2) as the single dialect.
3. Boundary rules as plugin rules with their own ids (I3, re-verified on 1.92.0).
4. Budgets, adopt-or-delete, agent-doc drift, layout geometry suite, `shot` + calibrated reviewer, series-palette computed check.
5. Preset smoke test: a fixture file per rule in the shipped preset, run in `make check` (invalid options abort the whole run).

Kill:

1. Regex guard `src/guard/index.ts` and `check-theme` text lanes for anything an AST/class rule covers.
2. The 4,382-line hand-written plugin's class/prop rules (raw-spacing family, card-inset, control-size-literal, raw-breakpoint prop forms): replaced by `@shadcn/lint` contracts + class patterns.
3. Grace ledger, retired-rule ids, `ai-sdk-major`, `forms-field-key`, Mantine CSS gates.
4. Fragment-scanning hook: run the engine on the post-edit file.

New for v3:

1. Preset = `@shadcn/lint` (rules + contracts per owned primitive, custom messages naming basalt variants) + `oxlint-tailwindcss` (`no-unknown-classes`, `no-default-palette`, `no-restricted-classes` patterns for `dark:`, viewport variants, `!`, `space-[xy]`, `z-[0-9]`, `enforce-sort-order` or oxfmt `sortTailwindcss`, never both) + basalt plugin (~10 residue rules, authored in TS with `@oxlint/plugins`, tested with `oxlint/plugins-dev` `RuleTester`).
2. Closed `@theme` shipped in the token CSS: `--color-*`, `--radius-*`, `--text-*`, `--shadow-*`, `--spacing`, plus the missing type-scale bridge.
3. Two lint zones: app/feature code strict; `components/ui/**` exempt from `no-restyle`/arbitrary/restricted-variant rules, protected by T9 (`shadcn add --diff` + `basalt-patch` marker).
4. `tsc` 7 for check-only (6.9x on PKG), TS 6 aliased only if a tool needs the API, `oxlint --type-aware` limited to a short list (floating promises, unsafe any). Needs `baseUrl` removed from consumer tsconfigs.
5. Hook: PostToolUse lint of the edited file + one Stop re-check, diagnostics only, terse output.
6. Stylelint 18 core rules over the emitted token CSS only (`color-no-hex`, `function-disallowed-list`, custom-property allow lists), as a repo-internal test, not a consumer burden.
7. Per-rule `--stats` and a waiver-per-kind budget.
8. A skills evaluation: before shipping any skill text, run a no-skill baseline on the same brief (Impeccable and Anthropic publish none); use basalt's seeded boards and the shot reviewer as the harness.

Open to the consumer: layout classes, grid templates by explicit allow, new variants/primitives by documented patch, series colours, page-internal composition inside container variants, own `DESIGN.md` winning over basalt rules.

## 10. Risks, unknowns, unverified

1. oxlint JS plugins are alpha with no GA date; both third-party plugins ride on it. Mitigation: ESLint 9 API compatibility (both ship for ESLint too); pin oxlint, run the preset smoke test on every bump. basalt is already pinned at 1.90.0 and the plugin API worked unchanged in 1.92.0.
2. `no-borrowed-component-styles` is experimental ("heuristics may change in a minor"); vendor-measured 1/6 on restyle-through-className (that is `@shadcn/lint`'s job). Treat as warn.
3. Single-maintainer `oxlint-tailwindcss`: fork-able MIT, 1.13 MB unpacked, but a v3 guarantee must not hinge on it; basalt's plugin owns what consumers rely on.
4. Not run: `eslint-plugin-tailwindcss` 4.4.0, stylelint 18 rules, `tsgolint` on the full PKG, `shadcn add --diff` on an edited file, the 80 KB DESIGN.md effect, any visual-regression tool. Impeccable's detector was not executed (docs and README only).
5. `@shadcn/lint` custom-message claims and evals are vendor numbers; I verified behaviour on the fixture and console, not the 150-run protocol.
6. Whether `bun` 1.4.4 + oxlint JS plugins behave in the consumer matrix (Bun 1.3+ documented by `@shadcn/lint`); worked here.
7. Tailwind: no switch to forbid arbitrary values found in docs (unchanged); `@source not inline` vs arbitrary candidates undocumented.
8. Owner decision for the architecture agent: the stack above assumes consumers copy-in shadcn sources under `components/ui` (zones, T9). An npm-dist `basalt-ui` would need the plugin rules to key on package import provenance instead; `@shadcn/lint` supports `componentImports`/`settings.shadcn.ui` prefixes for that, which I did not run.
