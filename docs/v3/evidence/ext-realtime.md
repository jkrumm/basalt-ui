# External + fleet evidence: keeping UI fresh (polling, SSE, WebSocket, invalidation, offline, stale)

Date 2026-11-09. Scope: server-state freshness as a framework concern for basalt-ui v3. (F) = observed fact with file:line;
(J) = my judgement; (W) = web fact with URL, from `agw research` runs 2026-11-09 and installed `node_modules` source.
Paths: `SF` = `~/SourceRoot/software-factory/apps/console/src`, `ARGO` = `~/SourceRoot/argo/apps/dashboard/src`, `BUI` =
`~/SourceRoot/basalt-ui/packages/basalt-ui/src`. Other-expert territory (not re-audited here): draft/synced-settings state, AI
token streaming, table chrome.

## 0. Headline

(F) The fleet has **six independent freshness implementations and zero shared code**: console (SSE + selective invalidation, ~360
lines), shutterflow (EventSource hub), epos teamchat (fetch-SSE follow loop), rollhook (fetch-SSE log reader + `setInterval`),
argo (25 hand-set `refetchInterval` sites), rb/linewatch (adaptive polling). basalt-ui 2.x ships only the _consuming_ half
(`QueryState`, `QueryStateLike`, `SyncButton`, `makeQueryClient`); the producing half (`./connectivity`, SSE + health) was deleted in 2.0
as "no consumer" (`MIGRATING.md:1027`) while the consumers kept re-growing it.
(J) v3 should ship ONE small `basalt-ui/live` module (~600-800 lines, pure TS + a few hooks): a transport-agnostic **channel** (fetch-based
SSE client, status store, backoff, watchdog), an **invalidation bridge** (frame -> query-key predicate, tiered debounce), a **`liveQuery`
options factory** (replaces every `refetchInterval` literal), a **connection/freshness store** with an indicator, and an optional
**snapshot persister**. WebSocket, multi-tab leader election, `streamedQuery` and TanStack DB are LEFT OPEN / on-notice, not wrapped.

(F) Server contract the client depends on (`apps/server/src/read/stream.ts:1-23`): cursor `<txid>.<seq>`, rows emitted only below
`pg_snapshot_xmin` so resume loses/doubles nothing; unknown cursor = `CursorGone` (410), client restarts from `GET /v1/changes`.
(J) The protocol (monotonic opaque cursor, `hello` greeting, 410 = restart, comment keepalive) is the contract a framework client should
state once; the Postgres mechanics are not framework business.

Defects in console wiring (J, each with the line that shows it):

1. **"Offline" over-triggers**: `failed = any query in status 'error'` makes the chip "Offline" and `useSettle` disable EVERY write
   (`connection.ts:36,46`, `settle.ts:41`). One failing endpoint (a 500) reads as no network.
2. **Two sources of truth for online**: the chip reads `navigator.onLine` directly (`connection.ts:35`); Query's `onlineManager`
   (`query-core/src/onlineManager.ts:16-35`, default `window online/offline`) independently pauses fetches. They can disagree.
3. **One EventSource per tab, no sharing** (`live.ts:104`). Harmless on HTTP/2 (W: MDN, stream limit defaults 100), a 6-socket hazard on
   HTTP/1.1 (W: MDN; "Won't fix" in Chrome and Firefox).
4. `useLive` has no server snapshot (above); `startLive` is a module side effect called from `main.tsx:15`, not a mount-scoped hook, so it
   cannot be torn down per test or per router (SSR-hostile).

(F) No connection indicator, no offline handling, no cache persistence (`self-state-runtime.md` section 1: "Not present anywhere:
SSE/WebSocket/polling helpers, query-cache persistence"). `QueryStateLike.fetchStatus` includes `'paused'` (`BUI/common/query-state-like.ts`),
so a paused (offline) first load renders as `pending` (`dashboard/query-state.tsx:213`), which says "Loading" with no hint the device is offline.
(J) Argo is the proof that polling covers a lot: 25 sites, all with a plausible cadence. What it lacks is the vocabulary and the
guard: no rule stops a 26th site from forgetting `InBackground:false` or the mount-once discipline.

## 9. Risks and open questions

1. (J) **Native `EventSource` vs fetch client is a real trade.** Fetch-SSE gives headers, status codes and byte-level watchdog, but loses the
   browser's built-in reconnect and bfcache behaviour; the console is the only app with long field evidence and it uses native
   `EventSource`. Mobile-Safari long-lived `fetch` stream behaviour is **unverified here**. Mitigation: the channel's transport is
   pluggable; port `shell-live.e2e.ts` first and run it against both.
2. (J) `liveQuery` owning a central timer means reimplementing part of Query's refetch scheduling; if it is only `queryOptions` + a shared
   `refetchInterval` function backed by a `pauseWhileMutating` store, the per-observer timer stays (cost: N observers = N fetches).
   Needs a spike with 6 observers on one key (the argo `WeightPopover`-per-row case, `gym.ts:46-52`) before choosing.
3. (J) Class names (`static/standard/ticker/pushed`) are mine; argo's 25 sites should be migrated to them in the argo-rewrite wave as the
   validation, not designed in the abstract.
4. (W) TanStack DB crosses to 1.0 final within weeks to months; the "re-evaluate" gate should be dated (after 1.0 final plus one minor),
   not left open-ended.
5. Server-side contract is out of scope but is the real constraint: a push channel needs a monotonic cursor and a replay-or-snapshot
   rule; epos and console both built it, rollhook has no resume (`seenCount` dedupe instead). The skill must say this or consumers will
   ship streams that lose frames on reconnect.
