# Evidence: basalt-ui's own chart system (self-charts)

Audited 2026-11-09 at master `6f1007a8`. Paths relative to `packages/basalt-ui/` unless prefixed `docs/`. "Observed" = read in code, docs or a tool run; "Judgement" = mine. Engine facts are from the installed `@tanstack/charts@1.1.0` (`node_modules/@tanstack/charts`) or the upstream release page read via `agw web read https://github.com/TanStack/charts/releases` (2026-11-09).

## 0. Verdict in six lines

- Observed: the chart layer is already almost Mantine-free. `src/charts/**` has zero `@mantine/*` imports; the entire Mantine residue is 2 CSS lines (`chart-box.module.css:226,232` use `--mantine-scale`), 1 DOM selector (`compile.ts:1091` `.mantine-Card-root`) and 3 imports from `src/dashboard` (`widget-header`, `delta-badge`, `visual-slot`), which are themselves Mantine-free.
- Observed: CI-enforced packaging means `./charts` renders with only react installed (`scripts/check-dist-layering.mjs`, `scripts/pack-test.sh`). Rewriting to shadcn/Tailwind 4 therefore touches the chart _engine layer_ very little and the _chrome_ (card, header, retry, delta, tooltip-clamp) a lot.
- Observed: the cost sits in bespoke chrome, not in marks. 9 244 prod TS/TSX lines + 714 CSS lines + 11 638 test lines; 163 commits touched `src/charts` since 2026-10-14, nearly all `fix:` polish on card/header/readout/tooltip geometry.
- Observed: the 2.x chart audit (`docs/waves/maturation-v2/charts.md`, 24 findings) is mostly **unlanded**: `height` still has no `'fill'` (`types.ts:350`), `highlighted` is still a definition input (`compile.ts:1370`), `CHART_TAGS` still omits `CartesianChart` (`configs/oxlint-plugin.js:676-686`), `useShallowStable` is still the memo story (`CartesianChart.tsx:61`). v3 is the chance to land them for free.
- Judgement: keep the rung (definition compiler plus one host), the series-as-single-source law, the CSS-owned height box, the cursor groups and the lint boundary. Redesign the series type, the card/header/stat-card split, tooltip clamping and the Sparkline readout. Drop Donut, MirroredBars, `foldBands`, public `chartCurve`.
- Judgement: v3 charts ship roughly 10 value exports (from 14) and about 6 500 prod lines (from 9 244) without losing a consumer-used capability.

### 7.3 Judgement: slimmest toolkit for rich cards

1. **One card anatomy, three bodies.** `MetricCard` (what the owner calls the stat card) and `ChartCard` converge: header (icon, title, subtitle, actions/menu) + inset panel (value row: hero, unit, delta badge, comparison line; then the visual; then `axisLabels` start/now/end) + footer (two key-values). A chart body (any kind) and a sparkline/bars body are just `children`/`visual`. Today `StatCard` renders its own anatomy and `ChartCard` goes through `WidgetHeader` (`stat-card.tsx:20-21`): two anatomies for one idea (they disagree on title font: `SPEC.md` 6.1 "ChartCard keeps its head-font title").
2. **A `Visual` slot contract** (`VisualSlotContext` generalised): the host publishes `{tone, loading, compact, height}`; sparkline, bars, meter, ring and any chart body read it. Keep the render-prop-over-measured-box idea or replace it with a CSS container (preferable: `@container` and `h-full`, no JS measurement).
3. **Sparkline = engine-hosted core + thin readout.** Keep pooling, `{at,value}`, reference, band, emphasis dot, `state`, and drop the 200-line chip geometry in favour of a fixed readout row (the console's x-labels row doubles as the readout: show hovered value in the "now" label slot). Target ≤ 450 lines (from 957). Add `future` (dashed segment after index n) and `axisLabels` because the owner's reference needs both. Bars variant uses the same code path (`mark: 'bar'`).
4. **Shared delta**: one `Delta` (`higherIsBetter`, text colour per DESIGN-CORE "deltas are text colour only" in `SPEC.md` 6.1 vs the owner's pill in the console reference; the owner's call for the badge shape) feeding both `ChartFact.comparison` and the metric card.
5. **Controls inside cards** (brief: "rich cards that carry their own controls or bind to global ones") are slot data on the card header (`actions`), exactly the existing `actions` slot law; keep the rule that a card control lives in exactly one home (`basalt/control-outside-home`).
6. **Hidden data table for every chart** (console `ChartFrame`) is a cheap a11y upgrade over the engine's single accessible SVG: Judgement, needs a decision on SSR payload size for 5k-point charts.

## 8. Risks and open questions

Real risks (Judgement):

- Visual regression is the main v3 risk because the major gate is lifted: 163 recent commits are pixel polish. Port the 13 layout tests and `make evidence` perf lane first and treat them as the acceptance gate.
- Exact-pin plus DOM scrape (`host.tsx:110-121`) will break on the 1.1 to 1.5 bump if the markup changed; do the bump first, behind the existing suite.
- Consumers: weatherorb is the heaviest _custom_ chart user (`CartesianChart` 6 files, `chartCursor` 9, `chartCurve` 6, `XZoneSpec` 7) and sits at 2.26.0; argo (153 chart-importing files, 110 `ChartCard` sites) migrates by codemod only if `ChartCard`'s props stay stable or a codemod ships.

Owner decisions (real, not defaults):

1. Sparkline renderer: stay on TanStack Charts (one theme/a11y/SSR path, +engine bytes on sparkline-only pages) or allow a tiny engine-free SVG core for sparklines/mini-bars as the factory console did (134 lines, no engine). Brief says TanStack only; I read that as covering cartesian charts. My tendency: TanStack for `Sparkline`, since 23 files depend on its pooling, band and reference features.
2. Does `ChartCard`/the card toolkit depend on the owned shadcn components (losing react-only `./charts`), or does `charts` stay headless with the card in the UI package. My tendency: the second.
3. Container-class thresholds: keep 240/480/800 as arbitrary container queries (retain `breakpoint-literals.test.ts`) or re-fit to Tailwind's `@xs/@sm/@lg` steps (320/384/512). My tendency: keep, since the height ladder is tuned to them.
