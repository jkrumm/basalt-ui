## Bottom line

**(1) Router view transitions.** TanStack Router has its **own** view-transition integration — the router-level `defaultViewTransition` option on `createRouter`, plus a per-navigation `viewTransition` option on `<Link>`, `useNavigate`, `<Navigate>` and `router.navigate` — both typed `boolean | ViewTransitionOptions` (with a `types` field that can be a static array or a `locationChangeInfo => string[] | false` callback). It calls `document.startViewTransition` **directly** and does **not** delegate to React's `<ViewTransition>`. There is **no official integration of React's `<ViewTransition>`/`addTransitionType`'s stable APIs with TanStack Router navigations**; the only documented bridge is a per-navigation `startTransition: true` option that wraps the navigation in `React.startTransition`. The reason your `<ViewTransition>`-wrapped `<Outlet>` measured 0 calls is confirmed in-repo: router match state is published through `@tanstack/react-store`'s `useSyncExternalStore`, which commits at a hardcoded SyncLane _outside_ any transition, so React never registers a view transition. Same-document view transitions are Baseline Newly Available (Chrome 111/Safari 18.0/Firefox 144); **view-transition _types_** are much narrower (Chrome/Edge 125, Safari 18.2, Firefox 147), and the router silently drops `types` where the selector is unsupported.

**(2) TanStack Start SSR.** Selective SSR is the route `ssr` option with exactly `true` (default) / `false` / `'data-only'`, overridable globally with `defaultSsr` in `createStart`; a child route may only be **more restrictive** than its parent (`true → 'data-only' → false`). The client-only escape hatch is `<ClientOnly>` from `@tanstack/react-router` (props `children`, `fallback`); there is **no** `clientOnly` route option. Streaming uses `<Await>` (from `@tanstack/react-router`) over an **unawaited promise** returned from a route loader, wrapped in `<Suspense>`; streaming SSR is flagged **experimental**, and an open bug (#7094) shows an unawaited loader promise can defeat streaming. **RSC is supported but experimental** in Start, is **not** enabled by default, and uses `renderServerComponent` / `createCompositeComponent` from `@tanstack/react-start/rsc` — **there is no `createServerComponent`**.

**(3) React 19.2/19.3 primitives.** `<ViewTransition>` and `addTransitionType` are **stable in React 19.3** (Sept 9, 2026) and were Canary/Experimental-only in 19.2. Partial prerendering is **stable** since 19.2 — but note the correction: `prerender`, `prerenderToNodeStream`, `resumeAndPrerender`, `resumeAndPrerenderToNodeStream` live in **`react-dom/static`**, while `resume` and `resumeToPipeableStream` live in **`react-dom/server`** (`resume` is _not_ exported from `react-dom/static`). Selective hydration is **automatic and Suspense-integrated with no stable public control API**. Suspense streaming SSR (`renderToReadableStream` / `renderToPipeableStream`) is stable.

## 1. Route view transitions: TanStack Router + React 19.3

### 1.1 The router's own API (this is the supported mechanism)

| Surface                                          | Option                  | Type                               |
| ------------------------------------------------ | ----------------------- | ---------------------------------- |
| `createRouter({...})`                            | `defaultViewTransition` | `boolean \| ViewTransitionOptions` |
| `<Link>`                                         | `viewTransition`        | `boolean \| ViewTransitionOptions` |
| `useNavigate` / `router.navigate` / `<Navigate>` | `viewTransition`        | `boolean \| ViewTransitionOptions` |

`defaultViewTransition` is exactly the router-level name and is typed `boolean | ViewTransitionOptions`; it is defined in `packages/router-core/src/router.ts` alongside a `shouldViewTransition` field ([RouterOptionsType docs](https://tanstack.com/router/latest/docs/api/router/RouterOptionsType), [router.ts](https://github.com/TanStack/router/blob/HEAD/packages/router-core/src/router.ts)). Per-navigation, `useNavigate`/`router.navigate` accept `viewTransition` of the same type ([NavigateOptionsType docs](https://tanstack.com/router/latest/docs/api/router/NavigateOptionsType)), and `<Link>` accepts its own `viewTransition` in `packages/router-core/src/link.ts` ([link.ts](https://github.com/tanstack/router/blob/main/packages/router-core/src/link.ts)).

**`ViewTransitionOptions.types` is the key capability for mapping routes to transition types.** It is a single field typed `Array<string>` **or** a function `(locationChangeInfo: { fromLocation?: ParsedLocation; toLocation: ParsedLocation; pathChanged: boolean; hrefChanged: boolean; hashChanged: boolean }) => Array<string> | false`. Returning `false` suppresses the transition for that navigation ([RouterOptionsType.md](https://github.com/tanstack/router/blob/main/docs/router/api/router/RouterOptionsType.md), [ViewTransitionOptionsType](https://tanstack.com/router/latest/docs/api/router/ViewTransitionOptionsType)). Because the **per-navigation** `viewTransition` also accepts a full `ViewTransitionOptions`, **types can be supplied per navigation** (static array or callback), not only globally ([NavigateOptionsType docs](https://tanstack.com/router/latest/docs/api/router/NavigateOptionsType)).

**Per-navigation and router-level resolve through the same code path.** `RouterCore.startViewTransition` does `const shouldViewTransition = this.shouldViewTransition ?? this.options.defaultViewTransition`, and `commitLocation` sets `this.shouldViewTransition = viewTransition`. `<Link>` forwards its prop via `router.navigate({ ...options, _fromLocation: dest._fromLocation })` (`viewTransition` is a router-consumed option key), and `buildAndCommitLocation` destructures `viewTransition` and passes it to `commitLocation` ([router.ts](https://github.com/TanStack/router/blob/HEAD/packages/router-core/src/router.ts), [link.tsx](https://github.com/TanStack/router/blob/HEAD/packages/react-router/src/link.tsx)). So a `<Link>` value and `defaultViewTransition` are indistinguishable downstream, and the `locationChangeInfo` callback shape is identical for both. `fromLocation` **is** populated for link-triggered navigations: it is `stores.resolvedLocation.get()`, which `runClientTransaction` sets _after_ each transition, so any subsequent navigation (i.e. every link click after the first) has the previous route; it is `undefined` only on the very first navigation of a session ([load-client.ts](https://github.com/TanStack/router/blob/HEAD/packages/router-core/src/load-client.ts)).

**Implementation detail you can rely on:** when `types` is a function, the router calls it with `getLocationChangeInfo(next, prevLocation)` where `next = this.latestLocation` and `prevLocation = this.stores.resolvedLocation.get()`; `getLocationChangeInfo` returns `{ fromLocation: resolvedLocation, toLocation: location, pathChanged: resolvedLocation?.pathname !== location.pathname, hrefChanged: resolvedLocation?.href !== location.href, hashChanged: resolvedLocation?.hash !== location.hash }` ([router.ts](https://github.com/TanStack/router/blob/HEAD/packages/router-core/src/router.ts)). The callback is only invoked when `window.CSS?.supports?.('selector(:active-view-transition-type(a))')` is true; otherwise the router calls `document.startViewTransition(fn)` and the callback never runs ([router.ts](https://github.com/TanStack/router/blob/HEAD/packages/router-core/src/router.ts)).

### 1.2 It calls the browser API directly — not React's `<ViewTransition>`

The router's `startViewTransition` path calls `document.startViewTransition` directly ([router.ts](https://github.com/TanStack/router/blob/HEAD/packages/router-core/src/router.ts)). At commit `88f366ab`, it calls `document.startViewTransition(startViewTransitionParams)` and does **not** store the returned `ViewTransition` object; it uses the object form `{ update, types }` only when `typeof shouldViewTransition === 'object'` **and** `isViewTransitionTypesSupported` is true, where `isViewTransitionTypesSupported = window.CSS.supports('selector(:active-view-transition-type(a))')` — falling back to the plain function form (types dropped) elsewhere ([router.ts @88f366ab](https://github.com/TanStack/router/blob/88f366ab8e049b23341f7dcea96c5065f630c31f/packages/router-core/src/router.ts)).

This explains your measurement directly. An in-repo RFC, discussion **#8188**, states plainly: _"React's `<ViewTransition>` never fires across a TanStack Router navigation."_ Every reactive read goes `useStore → useSyncExternalStoreWithSelector → useSyncExternalStore`, which React schedules at a hardcoded SyncLane (`enqueueConcurrentRenderForLane(fiber, 2)`) _after_ the `startTransition` scope has exited, so the update carrying the new route is never a transition. Its measured `document.startViewTransition` counts on React canary: `router.navigate()` inside `startTransition` 0→1, `<Link>` navigation 0→1 (before→after the proposed frame mechanism) — matching your 0/12 in Chrome 155 ([#8188](https://github.com/TanStack/router/discussions/8188)). Discussion **#8345** (ryansolid) agrees the `useSyncExternalStore` behaviour is _"a blocker on React side"_, adds that React's view transitions activate only for updates inside transitions/Suspense, and concludes: _"a navigation whose async lives outside React can't ever use it; we wrap `document.startViewTransition` by hand instead."_ Both are opt-in RFCs (`default off`), not merged fixes ([#8345](https://github.com/TanStack/router/discussions/8345)).

**Recommendation for basalt-ui:** for TanStack Router consumers, drive transitions with the router's `defaultViewTransition` / per-navigation `viewTransition` (not React's `<ViewTransition>` wrapping `<Outlet>`). Use React's `<ViewTransition>` only for state changes you control inside your own components that are wrapped in a transition.

### 1.3 Is there a `startTransition` opt-in? (a documented-but-contested bridge)

TanStack Router documents a per-navigation **`startTransition`** option on `<Link>`, `useNavigate`, `<Navigate>` and `router.navigate`, described as _"Wrap navigation in React.startTransition"_; the Link prop table groups `startTransition` and `viewTransition` under _"Transitions — Enable React or View Transitions"_ ([DeepWiki: Link Component and Navigation](https://deepwiki.com/tanstack/router/3.3-link-component-and-navigation)). A published copy of the docs types shows `/** Wrap navigation in startTransition */ startTransition?: boolean;` beside `viewTransition` ([tessl docs snapshot](https://tessl.io/registry/tessl/npm-tanstack--react-router/1.132.0/files/docs/react-components.md)). Setting `startTransition: true` wraps that click/imperative navigation in `React.startTransition`, which is the opt-in that would let React treat the route commit as a transition and thus drive React `<ViewTransition>`.

**Flag the discrepancy:** the _current official_ `NavigateOptionsType` docs page lists `replace`, `resetScroll`, `hashScrollIntoView`, `viewTransition`, `ignoreBlocker`, `reloadDocument`, `href` — it does **not** list `startTransition` ([NavigateOptionsType](https://tanstack.com/router/latest/docs/api/router/NavigateOptionsType)). So either `startTransition` is a `Link`/`useNavigate`-only prop or the type docs page is stale relative to the code; **the implementation of the `startTransition` option in `packages/react-router/src/link.tsx` could not be confirmed in source**, so treat the exact prop surface as provisional. There is **no confirmed router-level `defaultStartTransition`**; only `defaultViewTransition` was found in `RouterOptions`.

**No end-to-end proof.** No retrieved source demonstrates `<ViewTransition>` + TanStack Router `<Outlet>` actually working; treat the `startTransition: true` remedy for the `<ViewTransition>` case as documented-but-not-independently-verified. The ecosystem signal is directional: React Router **deprecated** its own `viewTransition` prop/`useViewTransitionState` in favour of React's `<ViewTransition>` component (requires React/React DOM 19.3+) — i.e. router-managed transitions are migrating to React-driven ones ([React Router view-transitions](https://reactrouter.com/main/how-to/view-transitions)).

### 1.4 Reliability problems, bugs and limitations (open)

- **Missed transitions on the react-store sync-commit path** — the 0-fire behaviour above (#8188, #8345). Proposals only, not shipped.
- **Unhandled promise rejections.** Discussion **#7733** documents `AbortError` / `InvalidStateError` / `TimeoutError` flooding Sentry — e.g. _"AbortError: Transition was skipped"_ at 994 events / 83 users over ~4 months, and `InvalidStateError` at 159 events / 47 users. Root cause traced to router-core discarding the `ViewTransition` object returned by `document.startViewTransition` without `.catch()` on `.ready`/`.finished` ([#7733](https://github.com/TanStack/router/discussions/7733)).
- **No nested/outlet transition API.** Discussion **#5670** is an open API-design proposal (`transitionComponent` / `useRegisterTransition`, `defaultViewTransition.mode: 'element'|'document'`) and states there is no shipped element-level API and that nested coordination _"needs confirmation through testing"_ ([#5670](https://github.com/TanStack/router/discussions/5670)).
- **`types` silently dropped where unsupported** — the router only passes `{update, types}` where `:active-view-transition-type()` is supported, otherwise it falls back to `document.startViewTransition(fn)` ([router.ts @88f366ab](https://github.com/TanStack/router/blob/88f366ab8e049b23341f7dcea96c5065f630c31f/packages/router-core/src/router.ts)).
- **History navigation.** Issue **#2983** reports `router.history` navigation not firing native transitions (reporter suspects the `notify()` call in the browser-history source cancels it); the search snippet associates it with a closed PR, but the PR number could not be confirmed from the page itself — treat as provisional ([#2983](https://github.com/TanStack/router/issues/2983)). _(Some numbers in that snippet were not present in the retrieved page text and are omitted.)_
- **Solid-specific breakage.** Issue **#3736** reports Solid-Router + `autoCodeSplitting: true` breaking `defaultViewTransition` while the identical React setup works; workaround is removing `autoCodeSplitting` ([#3736](https://github.com/TanStack/router/issues/3736)).
- No dedicated issue for _"navigate outside a user gesture"_ was located.

## 2. TanStack Start SSR patterns for dashboards

### 2.1 Selective SSR per route — `ssr: true | false | 'data-only'`

Configured on the route definition passed to `createFileRoute('/path')({...})` / `createRoute`. Its type is `SSROption = boolean | 'data-only'` (defined in `@tanstack/router-core`, shared with the router option `defaultSsr?: SSROption`) ([selective-ssr guide](https://tanstack.com/start/latest/docs/framework/react/guide/selective-ssr), [SSROption in router.ts](https://github.com/TanStack/router/blob/ac223be0/packages/router-core/src/router.ts)). If omitted it defaults to `true`; the global default is overridable with `defaultSsr` in `createStart` (`src/start.ts`) ([selective-ssr guide](https://tanstack.com/start/latest/docs/framework/react/guide/selective-ssr), [start-client-core SKILL.md](https://app.unpkg.com/@tanstack/start-client-core@1.169.4/files/skills/start-core/deployment/SKILL.md)).

**Exact semantics:**

- `ssr: true` (default) — `beforeLoad` runs on the server (context sent to client), `loader` runs on the server (data sent to client), and the component is **server-rendered to HTML**.
- `ssr: false` — server execution of the route's `beforeLoad` **and** `loader` is disabled, **and** the component is not server-rendered (fully client-only).
- `ssr: 'data-only'` — hybrid: `beforeLoad` + `loader` **do** run on the server (context + data sent to client), but the component is **not** server-rendered. This is the recommended mode for "keep the data, skip server rendering" cases such as browser-API-heavy widgets. ([selective-ssr guide](https://tanstack.com/start/latest/docs/framework/react/guide/selective-ssr), [LogRocket write-up](https://blog.logrocket.com/selective-ssr-tanstack-start/))

**Functional form:** `ssr: ({ params, search }) => SSROption | undefined`, run only on the server during the initial request and stripped from the client bundle; `params`/`search` arrive post-validation as discriminated unions (`{ status:'success', value }` / `{ status:'error', error }`) ([selective-ssr guide](https://tanstack.com/start/latest/docs/framework/react/guide/selective-ssr)).

**Inheritance:** a child inherits its parent's config and may only change it to be _more restrictive_ — `true → 'data-only' → false`; a less-restrictive child value is ignored ([selective-ssr guide](https://tanstack.com/start/latest/docs/framework/react/guide/selective-ssr)). **Fallback:** the first non-SSR route renders its `pendingComponent` (else `defaultPendingComponent`, else nothing) on the server; on hydration it shows for at least `minPendingMs` ([selective-ssr guide](https://tanstack.com/start/latest/docs/framework/react/guide/selective-ssr)). **Root caveat:** you can disable SSR of the root route component, but the `<html>` shell must still be SSR'd via `shellComponent` ([selective-ssr guide](https://tanstack.com/start/latest/docs/framework/react/guide/selective-ssr)).

### 2.2 Client-only islands — `<ClientOnly>` (and no `clientOnly` route option)

`<ClientOnly>` is imported from `@tanstack/react-router`: `import { ClientOnly } from '@tanstack/react-router'`. Props: `children` (required) and `fallback` (optional, defaults to `null`). Internally it returns `useHydrated() ? children : fallback`, where `useHydrated()` is a `useSyncExternalStore` whose server snapshot is `false` — so `fallback` renders during SSR and the first client render, and `children` after hydration ([clientOnlyComponent docs](https://tanstack.com/router/latest/docs/api/router/clientOnlyComponent), [ClientOnly.tsx](https://github.com/TanStack/router/blob/HEAD/packages/react-router/src/ClientOnly.tsx)). Documented dashboard pattern:

```tsx
<ClientOnly fallback={<FallbackCharts />}>
  <Charts />
</ClientOnly>
```

TanStack Start also exposes `createClientOnlyFn(fn)` (throws on the server) and the `useHydrated` hook ([execution-model guide](https://tanstack.com/start/latest/docs/framework/react/guide/execution-model)). **There is no `clientOnly` route option.** The only documented per-route SSR controls are `ssr` and `defaultSsr`; `clientOnly: [...]` was only a user _proposal_ in discussion #2454, and a maintainer replied that per-route `ssr: false` was shipped instead (release v1.59.0), referencing `<ClientOnly>` as the component-level escape hatch ([discussion #2454](https://github.com/TanStack/router/discussions/2454)).

### 2.3 Streaming SSR and deferred loader data

Start uses Router's SSR pipeline, which offers a buffering handler (`defaultRenderHandler`) vs a streaming one (`defaultStreamHandler` / `renderRouterToStream`). The how-to shows `renderRouterToStream({ request, responseHeaders, router, children })` and states you use it "when you need the server to render suspended content after it resolves." For streaming, Router's `<Scripts />` must be rendered **inside `<body>`** of the root route ([setup-ssr how-to](https://tanstack.com/router/latest/docs/how-to/setup-ssr), [SSR guide](https://tanstack.com/router/latest/docs/guide/ssr)). The SSR guide flags **streaming SSR as experimental**.

**Deferred/streamed loader data:** a route `loader` returns an object containing an **unawaited promise**; the router resolves it later ([deferred-data-loading guide](https://tanstack.com/router/latest/docs/guide/deferred-data-loading)). Consumption uses **`<Await>`** (`import { Await } from '@tanstack/react-router'`), whose API takes `promise: Promise<T>` and `children: (result: T) => React.ReactNode`, and must be wrapped in `<Suspense>` so the boundary suspends until the promise resolves ([awaitComponent API](https://tanstack.com/router/latest/docs/api/router/awaitComponent), [deferred-data example](https://tanstack.com/router/latest/docs/framework/react/examples/deferred-data), [e2e deferred.tsx](https://github.com/TanStack/router/blob/HEAD/e2e/react-start/basic/src/routes/deferred.tsx)). A **`defer`** helper exists (`deferFunction` API) to wrap a promise into a deferred state object for `<Await>`/`useAwaited`, but the docs note calling `defer` manually is **no longer required** because promises are handled automatically ([deferFunction API](https://tanstack.com/router/latest/docs/api/router/deferFunction)).

**Interaction with selective SSR:** `ssr: false` emits the route's `pendingComponent` (or nothing) as the server fallback, while `'data-only'` renders the loader data without the component ([selective-ssr guide](https://tanstack.com/start/latest/docs/framework/react/guide/selective-ssr)). **Known streaming bug:** issue **#7094** reports that an unawaited promise held in a route loader can **block streaming** — the server buffers the whole response instead of flushing the shell first — so ordering matters: keep the awaited promise inside a `<Suspense>` boundary so the shell can flush ([#7094](https://github.com/TanStack/router/issues/7094)).

### 2.4 Recommended dashboard patterns (charts, large tables, live data)

Synthesized from the above (not a single named doc page):

1. **Keep the shell unsuspended.** The header/nav/layout renders with no promise in its path so the first paint flushes immediately.
2. **Isolate each slow part** (chart, large table, live feed) in its own child component that (a) receives an **unawaited** promise from the route loader and (b) renders `<Await>` inside `<Suspense fallback={<Skeleton/>}>`. This streams the section in after the shell.
3. **For a route that must not SSR a component** but still wants server-fetched data, use `ssr: 'data-only'`; for widgets that touch browser-only APIs, wrap them in `<ClientOnly fallback={...}>` or set the route to `ssr: false` and rely on `pendingComponent`/`shellComponent`.
4. **RSC (experimental)** deferred/lazy components use a promise consumed with `React.use()` inside `<Suspense>` ([server-components guide](https://tanstack.com/start/latest/docs/framework/react/guide/server-components)).

For your baseline specifically: TanStack Charts 1.1 is SVG and `renderToString` works (per your background), so chart markup can be server-rendered — but note **React 19.2+ batches Suspense reveals** on the server, which affects how much of a large dashboard flushes per chunk (see §3.3).

### 2.5 React Server Components in TanStack Start — supported but **experimental**

Start itself is stable — _"TanStack Start is stable"_, 1.0 announced Oct 13, 2026 — yet the RSC docs carry the banner _"Server Components are experimental! The API may see refinements."_ and the Overview page states _"React Server Components are available as an experimental feature"_ ([Overview](https://tanstack.com/start/latest/docs/framework/react/overview), [server-components guide](https://tanstack.com/start/latest/docs/framework/react/guide/server-components), [Start blog index](https://tanstack.com/start/latest/docs/blog)). The April 2026 RSC post says RSC _"is experimental in TanStack Start RC and will remain experimental into early v1"_ and _"expect refinements while the feature is experimental"_ ([RSC blog](https://tanstack.com/blog/react-server-components)). So **RSC remained experimental after Start 1.0 shipped.**

**Not enabled by default** — you must install build-tool-specific RSC dependencies and configure the build plugin; requirements are React 19+, Vite 8+ or Rsbuild 2+ ([server-components guide](https://tanstack.com/start/latest/docs/framework/react/guide/server-components)).

**Exact API — there is no `createServerComponent`.** The two high-level helpers are:

- `renderServerComponent(<Element />)` → returns a renderable value you inline; **no slots**.
- `createCompositeComponent((props) => <Element />)` → returns a composite source rendered via `<CompositeComponent src={...} />`; **supports slots** (children, render props, component props).

Both import from **`@tanstack/react-start/rsc`** (independently confirmed by the ESLint rule `@tanstack/start/no-client-code-in-server-component`) ([server-components guide](https://tanstack.com/start/latest/docs/framework/react/guide/server-components), [ESLint rule](https://tanstack.com/start/latest/docs/eslint/no-client-code-in-server-component)). Low-level Flight APIs, same import: `renderToReadableStream` (server functions only), `createFromReadableStream` (client/SSR), `createFromFetch` (client).

**Relationship to server functions/routes:** RSCs are created/returned on the server — typically inside a `createServerFn` and returned through a route loader: _"Server functions can return Server Components - server-rendered React components that the client can compose."_ ([server-functions guide](https://tanstack.com/start/latest/docs/framework/react/guide/server-functions)). Start intentionally does **not** support `'use server'` actions; it requires explicit RPCs via `createServerFn` ([RSC blog](https://tanstack.com/blog/react-server-components)).

**Documented limitations:** slots are opaque on the server (`React.Children.map`/`cloneElement` don't work on `props.children`); render-prop/slot args must be serializable Flight values (strings, numbers, booleans, null, plain objects, arrays); Start's custom serialization isn't available in server components yet (primitives, Dates, React elements work); `renderServerComponent` values support no slots; the API _"may see refinements"_; component-level error isolation requires deferred loading; with React Query you must set `structuralSharing: false` ([server-components guide](https://tanstack.com/start/latest/docs/framework/react/guide/server-components)). Notably, **TanStack's own site dropped RSC** (_"We Stopped Using RSC on TanStack.com"_, Jul 24, 2026) — a site-level choice, **not** removal of framework support ([Start blog index](https://tanstack.com/start/latest/docs/blog)).

## 3. React 19.2 / 19.3 streaming and hydration primitives

Current stable React is **19.3.0** (published Sept 9, 2026; npm `latest`, with canary/experimental aligned to 19.3.0-*) ([npm react](https://www.npmjs.com/package/react)). **19.3 changed none of the static/streaming/hydration APIs** — it made ViewTransition and Fragment Refs stable and added `browser()`, Trusted Types support and RSC Context rendering ([React 19.3 blog](https://react.dev/blog/2026/09/09/react-19-3)).

### 3.1 `<ViewTransition>` and `addTransitionType` — stable in 19.3, canary in 19.2

Both are imported from **`react`** (not `react-dom`): `import { ViewTransition } from 'react'` and `import { startTransition, addTransitionType } from 'react'` ([ViewTransition](https://react.dev/reference/react/ViewTransition), [addTransitionType](https://react.dev/reference/react/addTransitionType)). 19.3 blog: _"We're excited to announce that both of these are now stable in React 19.3!"_ and _"in 19.3 it's stable and ready to use"_ ([React 19.3 blog](https://react.dev/blog/2026/09/09/react-19-3)). In 19.2 they were **Canary/Experimental only** (the react.dev reference pages carried a Canary banner; the React 19.2 blog lists only Activity, useEffectEvent, cacheSignal, Performance Tracks and partial pre-rendering, referencing `<ViewTransition>` only as future work) ([React 19.2 blog](https://react.dev/blog/2025/10/01/react-19-2), [addTransitionType.md](https://react.dev/reference/react/addTransitionType.md)).

**`<ViewTransition>` props:** `name` (string | object, for shared-element transitions; otherwise React auto-generates one). **View Transition Class props** — `enter`, `exit`, `update`, `share`, `default` — each accepts `"auto" | "none" | <classname> | object`, where object is `{[type]: value, default: value}`; `default="none"` turns off all other triggers unless explicitly listed. **View Transition Event props** — `onEnter`, `onExit`, `onShare`, `onUpdate` — each receives `(instance, types)` where `instance` exposes `old`, `new`, `name`, `group`, `imagePair` and `types` is `Array<string>`; only one event fires per boundary per Transition (`onShare` > `onEnter`/`onExit`), and each should return a cleanup function ([ViewTransition.md](https://react.dev/reference/react/ViewTransition.md)).

**When a transition activates (this is the crux for your Outlet problem):** React itself calls `document.startViewTransition` — never call it yourself. A view transition is registered **only when the state update is part of a Transition**. The reference caveat: _"By default, setState updates immediately and does not activate `<ViewTransition>`, only updates wrapped in a Transition, `<Suspense>`, or useDeferredValue activate ViewTransition."_ Activating sources are state updates inside `startTransition`/`useTransition`, a `<Suspense>` reveal, or a `useDeferredValue` update ([ViewTransition](https://react.dev/reference/react/ViewTransition), [React 19.3 blog](https://react.dev/blog/2026/09/09/react-19-3)). **Async actions:** in `startTransition(action)`, awaited calls are included in the transition, but _"currently require wrapping any set functions after the await in an additional startTransition"_ — a setState after `await` without a nested `startTransition` is **not** a Transition, and updates in `setTimeout` are never Transitions ([startTransition](https://react.dev/reference/react/startTransition), [useTransition](https://react.dev/reference/react/useTransition)). **Structural rule:** for `enter`/`exit` the `<ViewTransition>` must sit _before_ any DOM node (top-level), else no animation; `share` requires the same `name` on a removed and an inserted subtree in the same Transition (both in viewport) and takes precedence over enter/exit ([ViewTransition.md](https://react.dev/reference/react/ViewTransition.md)).

**`addTransitionType(type)`** is called inside a `startTransition` scope; `type` is any string; it returns nothing. Types are collected (multiple allowed, combined across transitions) and reset after each commit; a `<Suspense>` fallback associates the types, but revealing the content does not ([addTransitionType](https://react.dev/reference/react/addTransitionType), [addTransitionType.md](https://react.dev/reference/react/addTransitionType.md)). An independent write-up summarises: _"No Transition, no snapshot, no animation"_ ([dev.to](https://dev.to/parsajiravand/react-193-viewtransition-animate-state-without-losing-it-4kpp)).

### 3.2 Partial prerendering — **stable since 19.2** (with an import-path correction)

**Premise correction:** `resume` is **not** exported from `react-dom/static`. `react-dom/static` exports exactly four functions: `prerender`, `prerenderToNodeStream`, `resumeAndPrerender`, `resumeAndPrerenderToNodeStream`. The streaming `resume` and `resumeToPipeableStream` come from **`react-dom/server`** ([static.node.js](https://github.com/facebook/react/blob/HEAD/packages/react-dom/static.node.js), [server.node.js](https://github.com/facebook/react/blob/HEAD/packages/react-dom/server.node.js), [react-dom/static index](https://react.dev/reference/react-dom/static), [react-dom/server index](https://react.dev/reference/react-dom/server), [react-dom package.json](https://github.com/facebook/react/blob/HEAD/packages/react-dom/package.json)).

Exact signatures:

- `const { prelude, postponed } = await prerender(reactNode, options?)` → `prelude` is a Readable Web Stream, `postponed` a JSON-serializable opaque object (or `null`). Options: `bootstrapScriptContent`, `bootstrapScripts`, `bootstrapModules`, `identifierPrefix`, `importMap`, `maxHeadersLength`, `namespaceURI`, `onBrowserBailout`, `onError`, `onHeaders`, `progressiveChunkSize`, `signal` (no `nonce`) ([prerender](https://react.dev/reference/react-dom/static/prerender)).
- `const stream = await resume(reactNode, postponedState, options?)` → a Promise resolving to a Readable Web Stream with an extra `allReady` promise. Options: `nonce`, `signal`, `onBrowserBailout`, `onError` (no bootstrap/identifierPrefix options) ([resume](https://react.dev/reference/react-dom/server/resume)).
- `const { prelude, postponed } = await resumeAndPrerender(reactNode, postponedState, options?)`; options: `signal`, `onBrowserBailout`, `onError` ([resumeAndPrerender](https://react.dev/reference/react-dom/static/resumeAndPrerender)).

Status: shipped as a **stable** React DOM feature in **19.2** under "New React DOM Features → Partial Pre-rendering"; the react.dev docs pages carry **no Canary badge** (their markdown frontmatter is only `title:`) — only a sub-behaviour (`importMap`'s nonce handling) is documented "Canary only" ([React 19.2 blog](https://react.dev/blog/2025/10/01/react-19-2), [resume.md frontmatter](https://github.com/reactjs/react.dev/blob/HEAD/src/content/reference/react-dom/server/resume.md)). (End-to-end PPR in a _framework_ is a separate question.)

**Docs typo to watch:** the react.dev `resume` doc tells Node.js users to use `resumeToNodeStream`, but the actual Node export is `resumeToPipeableStream` — name your import `resumeToPipeableStream` ([resume.md](https://github.com/reactjs/react.dev/blob/HEAD/src/content/reference/react-dom/server/resume.md)).

### 3.3 Selective hydration — automatic, **no stable public control API**

Dehydrated Suspense boundaries hydrate on demand: discrete events (click/keypress) trigger synchronous selective hydration in the capture phase if the boundary's code is ready; hovered/focused boundaries get increased priority; otherwise boundaries hydrate in idle cycles ([React 18 working group](https://github.com/reactwg/react-18/discussions/130)). The only priority knob is the internal `unstable_scheduleHydration`, which is not documented on react.dev, and **issue #31099 states React provides no API to set hydration priority** on a component or Suspense boundary ([#31099](https://github.com/facebook/react/issues/31099)). `hydrateRoot(domNode, reactNode, options?)` exposes only `onCaughtError`, `onUncaughtError`, `onRecoverableError`, `identifierPrefix`, `formState` — none for selective hydration ([hydrateRoot](https://react.dev/reference/react-dom/client/hydrateRoot)). The `<Suspense>` reference confirms Selective Hydration is an under-the-hood optimization integrated with Suspense, not a separately-called API ([Suspense](https://react.dev/reference/react/Suspense)).

### 3.4 Suspense streaming SSR — **stable**

`renderToReadableStream(reactNode, options?)` returns a Promise resolving to a Readable Web Stream with an `allReady` property; `renderToPipeableStream(reactNode, options?)` returns `{ pipe, abort }` — both documented in react-dom@19.3 without a Canary badge ([renderToReadableStream](https://react.dev/reference/react-dom/server/renderToReadableStream), [renderToPipeableStream](https://react.dev/reference/react-dom/server/renderToPipeableStream)). **React 19.2 behavioural change:** React now **batches reveals** of server-rendered Suspense boundaries for a short time (a heuristic that backs off near the 2.5s LCP target) and added Node Web Streams support for `renderToReadableStream` and `prerender` ([React 19.2 blog](https://react.dev/blog/2025/10/01/react-19-2)). This batching is relevant to dashboards: a page with many streamed sections will flush them in groups rather than strictly independently.

## Practical summary for basalt-ui 2.0

- **Router transitions:** use `defaultViewTransition` and/or per-navigation `viewTransition` (with `types`) on TanStack Router; do not expect React's `<ViewTransition>` around `<Outlet>` to fire, because router state commits through `useSyncExternalStore` outside any transition (confirmed by #8188/#8345 and your 0/12 Chrome 155 result). If you want React's `<ViewTransition>` for router-driven UI, the only documented (unverified-in-source) bridge is `startTransition: true` on the navigation.
- **Version pin:** `@tanstack/react-router` `latest` = `1.170.44` (core `@tanstack/router-core` = `1.171.37`); `@tanstack/react-start` `latest` = `1.169.1` (published 2026-10-13, depends on react-router 1.170.44).
- **SSR:** compose selective SSR (`ssr: 'data-only'` for data-without-render, `ssr: false` + `<ClientOnly>` for browser-only widgets) with `<Await>`/`<Suspense>` streaming; keep the shell promise-free; streaming SSR is experimental and can be defeated by an unawaited loader promise (#7094).
- **RSC:** experimental; enable explicitly; `renderServerComponent` / `createCompositeComponent` from `@tanstack/react-start/rsc` (no `createServerComponent`).
